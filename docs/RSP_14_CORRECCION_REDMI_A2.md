2. **Causa raíz confirmada.** `OfflinePage.editar()` llamaba a `offline.foto(draft)` y obtenía un File, pero sólo lo usaba para mostrar un mensaje. Nunca pasaba ese resultado al formulario ni reconstruía una URI persistida para el `<img>`. El formulario nuevo quedaba con `fotoVistaPrevia=null`, `fotoFile=null` y sin `pozo.foto_url`. Por ello no podía mostrar la foto al reabrir, incluso si estaba correctamente guardada en disco. La implementación anterior ya esperaba `Filesystem.writeFile` en `Directory.Data` y persistía una ruta relativa: no hay evidencia para afirmar que Camera borró esa copia. No se inspeccionó el filesystem del Redmi: no puede asegurarse que el archivo de aquella prueba siga existiendo. Se corrige el defecto verificable de restauración y se refuerza la escritura/lectura nativa.

3. **Archivos.** Nueve archivos modificados y dos nuevos, incluido este informe. El estado exacto figura en el punto 18. No hay cambios de API, esquema, dependencias, configuración CSP o secure storage.

4. **Ciclo de fotografía.** Camera entrega `path`/`webPath` temporales; FotoComponent lee inmediatamente el `webPath`, valida JPEG/PNG/tamaño y emite un File. El object URL sólo sirve de vista previa. Al guardar, el repositorio escribe los bytes binarios mediante base64 sin Encoding.UTF8 en `Directory.Data/offline-v1/<sha256-origin>/<usuario>/<UUID-local>/photo-<UUID-foto>.jpg|png`. Espera la escritura y relee/compara el contenido antes de confirmar metadata. El JSON guarda únicamente la ruta relativa y MIME; se escribe a un temporal y se renombra a revisión inmutable. Al reabrir se recarga metadata, valida pertenencia/ruta, comprueba `stat` (archivo no vacío), obtiene `getUri` y aplica `Capacitor.convertFileSrc`. Esa URI se entrega al formulario mediante `fotoLocalUri` y se renderiza con `[src]` local, sin tratarla como recurso remoto autenticado. El futuro upload lee el mismo archivo permanente con `photoBase64`. Los nombres nuevos llevan extensión para facilitar MIME en WebView; se admiten los archivos RSP-14 anteriores sin extensión. No se guarda ningún URI temporal, blob URL ni base64 en el JSON. El contrato de `getUri` está documentado en el [repositorio oficial Filesystem](https://github.com/ionic-team/capacitor-filesystem).

5. **Errores y reemplazo.** Si la copia o verificación falla, se intenta guardar metadata recuperable con `fotoPendiente=true`, mensaje de error y referencia anterior intacta. No se muestra éxito completo y no se sincroniza ese borrador hasta guardar correctamente la foto. El File nuevo permanece en el formulario abierto para reintentar. Si también falla la metadata, se informa que los cambios siguen en pantalla y debe reintentarse antes de salir; la última revisión confirmada permanece. Después de salir/cerrar sin guardar correctamente una foto, puede ser necesario volver a tomarla/seleccionarla: no se promete recuperar bytes que no pudieron escribirse. Para preservar aislamiento entre cuentas se descarta el editor en memoria al salir. Un reemplazo usa otro nombre, sin sobrescribir la foto anterior. Se conserva la revisión previa y su foto; sólo al quedar sin referencias en las revisiones retenidas se intenta limpiar una foto de una revisión obsoleta. No hay barrido de fotos pendientes/huérfanas. La eliminación explícita del borrador sí incluye esos archivos propios.

6. **Eliminar borrador.** Confirmación Ionic explícita; cancelar, volver atrás o cerrar no elimina. Nunca enviado (`enviado` falso/ausente, sin estado sincronizando/sincronizado ni resultado): permite Eliminar borrador. Clave anterior cerrada autoritativamente sin creación: permite Eliminar borrador porque el mecanismo existente dejó `enviado=false` y cerró irrevocablemente la clave anterior. Sincronizando, respuesta perdida, timeout, 401, 5xx o conflicto con cierre no confirmado: no permite eliminar ni olvidar UUID. Exige reintentar el mecanismo existente hasta obtener resolución autoritativa. Creación confirmada (`sincronizado` más resultado con id y número): únicamente Eliminar copia local; conserva el pozo remoto y no hace DELETE HTTP. Estados inconsistentes como sincronizado sin resultado quedan bloqueados.

7. **Idempotencia y borrado interrumpido.** El servicio serializa borrar con guardar y sincronizar, y el repositorio relee el estado persistido antes de autorizar. No confía en el objeto mostrado ni en un 4xx aislado. No se cambió la generación/cierre autoritativo de claves ni single-flight. Para borrar, se renombra el directorio completo a `deleted-<UUID>` dentro del mismo espacio privado y después se elimina recursivamente sólo ese directorio. Si se interrumpe la limpieza, las revisiones retiradas no reaparecen en la cola ni pueden reenviarse; el siguiente listado reintenta limpiar únicamente directorios retirados explícitamente. Un fallo anterior al rename conserva el borrador. Las rutas se validan dentro de backend + usuario + UUID; no se eliminan temporales globales de Camera ni archivos de otros borradores.
